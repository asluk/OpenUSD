# Proposal-derived build loop

1. Consolidate and pin one complete proposal draft and its normative references. The proposal itself contains the functional requirements, authored data model and normative runtime behavior; separate implementation notes and research drafts are not additional authority. Keep the exact Git revision, any local draft changes and the full document's SHA-256. Verify the snapshot against the selected Git blob and regenerate every excerpt and trace from that snapshot; a cached hash alone does not prove it is the latest selected authority. Read background, design, decisions and examples along with every functional requirement. Label a complete proposed contract as a review candidate separately from group adoption; publication is not a substitute for completeness.
2. Derive the authored data model and observable runtime behavior. Cite the existing answer first. Identify the smallest missing authored fact or observable meaning, distinguishing design gaps, conflicting text, implementation freedom and unfinished verification.
3. Audit document completeness before implementation, then draft the necessary proposal repair. Trace every initial-scope requirement to authored facts, observable behavior and an independently derivable expected result. Check composition, defaults, interpolation, coordinate meanings, transform order, visible failures, resource responsibility and exports where applicable. Missing required contracts stop dependent implementation and trigger repair work. Re-read recorded decisions and normative prior art, and propose the smallest complete repair justified by requirements and USD semantics. Label newly proposed details separately from agreed direction; an agreement to add placement attributes requires concrete field proposals, not passive waiting. Assess whether the repair adds avoidable facts or merely promotes a prototype workaround. Do not replace the shared proposal with an experimental model, infer fields from fixtures or stash an implementation workaround in normative prose. An unresolved initial-scope requirement must not be silently deferred while still being advertised as satisfied. Pin the complete revised candidate before execution and identify it precisely when reporting conformance; partner adoption remains a separate status.
4. Define and inspect the consumer integration before execution. Trace each path from authored input through stage/data access and conversion to the actual output destination. Name the application host separately from the USD reader, conversion library and geometry/rendering backend. Record shared libraries and reused algorithms. Plan distinguishing end-to-end controls for every intended capability: coordinate queries, complete model placement, runtime geometry writeback, rendering and scene export. Reading a source attribute or returning an origin does not establish placement of geometry. Inspect the launched executable/target and the executed call path, rather than trusting an application or file name. Freeze that source inspection with the implementation.
5. Execute independently defined controls. Freeze the derived source before execution. Read authored fixtures using the selected query and integration paths. Compare each with an authority-derived expected result, not merely with each other. Record actual dependencies, source preservation, expected failures and the final consumer output. OpenUSD Python hosted in Omniverse remains an OpenUSD query path unless results demonstrably reach an OV-specific backend. Agreement across hosts does not establish independent geodetic engines.
6. Audit after implementation. Trace every authored geospatial field and observable interpretation back to the proposal. Check the reverse trace for required results absent from tests. Internal implementation choices must not invent scene facts or normalize unspecified syntax. Separately re-read the executed input-to-output call paths and compare every claimed capability with an end-to-end observation from that run. Missing consumer outputs stop the corresponding claim. Changed source invalidates the integration inspection. Do not repair a reporting overclaim by inventing requirements, adding prototype fields or accepting matching numbers as proof of downstream integration.
7. Assess and deliver the actual run. Write for a reader unfamiliar with geospatial concepts and OpenUSD: begin with the problem, define terms when needed, and explain what the run establishes about the proposal before giving test totals. Bind each demonstration to a functional requirement and exact proposal clause; state its expected behavior, observation, implication for proposal quality and limits. Label illustrations, synthetic datasets and recorded consumer output distinctly. Separate missing or conflicting model meaning, proposed choices awaiting agreement, implementation failures, unverified coverage and deferred scope. Include later audit findings without rewriting the original receipt. Derive the README from this assessment and frozen evidence, then derive the review body and editable slides from the README. Use explanatory images and readable comparisons, with technical detail in supporting sections. Inspect the rendered README and every final slide for comprehension, terminology, legibility and honest image interpretation; structural checks alone cannot establish human understanding. Run the integration-claim and assessment checks on the actual README, story, review body and final slide/notes/chart text, including negative controls for omitted limits, missing audit findings and stale evidence. Replace current delivery artifacts together and retain historical evidence in Git history. Publish to the existing fork draft when authorized.

The current candidate runner executes the exact pinned input-only placement model, fixed adjustment chart, native external-data association, Profiles, independent prototypes and geographic Cartesian scene chart. It compiles independent C++ placement and Hydra targets, checks pointwise queries and normal transport, verifies actual OV runtime writeback, and rereads geometry/CF/time-sampled exports. Proposal completeness means a complete proposed contract; it does not mean author agreement or whole-proposal conformance. Continuous nonlinear certificates and broader consumer coverage remain explicitly separate verification obligations.

Two placement implementations read the candidate: Python and C++. The OV sink reuses Python placement; the Hydra sink consumes a C++-resolved ordinary USD export. All coordinate conversion uses PROJ and external format decoding is shared. No third independent placement engine, OV rendering, live geospatial Hydra filter or physics integration is claimed.

Current delivery is derived by `collateral/derive_contract_delivery.py`, `collateral/human_delivery.py`, `collateral/contract_slides.mjs` and `collateral/verify_contract_delivery.py`. The README is the source for review body and slide narrative. `collateral/delivery-assessment.json` binds the informative assessment to the exact proposal, execution and later audit; a changed source requires reassessment. Their claims must agree with delivery/integration-evidence.json and the frozen source/run receipt. Prior generators and adapters are retained for historical reproducibility and are excluded from the active entry point.

## Split proposal authority

When terms/requirements and the full model/runtime candidate are separated,
execute against the exact full follow-up Git blob, never the reduced baseline.
Regenerate active plan/audit documents as well as excerpts and trace hashes;
freeze them with executed code. Check that descriptions of settled meaning,
pending model adoption and unsupported verification do not contradict each
other. Retest independent failures, not only the adapter's accepted fixtures.
