# Proposal-derived build loop

1. Consolidate and pin one complete proposal draft and its normative references. The proposal itself contains the functional requirements, authored data model and normative runtime behavior; separate implementation notes and research drafts are not additional authority. Keep the exact Git revision, any local draft changes and the full document's SHA-256. Read background, design, decisions and examples along with every functional requirement. Label a complete proposed contract as a review candidate separately from group adoption; publication is not a substitute for completeness.
2. Derive the authored data model and observable runtime behavior. Cite the existing answer first. Identify the smallest missing authored fact or observable meaning, distinguishing design gaps, conflicting text, implementation freedom and unfinished verification.
3. Audit document completeness before implementation, then draft the necessary proposal repair. Trace every initial-scope requirement to authored facts, observable behavior and an independently derivable expected result. Check composition, defaults, interpolation, coordinate meanings, transform order, visible failures, resource responsibility and exports where applicable. Missing required contracts stop dependent implementation and trigger repair work. Re-read recorded decisions and normative prior art, and propose the smallest complete repair justified by requirements and USD semantics. Label newly proposed details separately from agreed direction; an agreement to add placement attributes requires concrete field proposals, not passive waiting. Assess whether the repair adds avoidable facts or merely promotes a prototype workaround. Do not replace the shared proposal with an experimental model, infer fields from fixtures or stash an implementation workaround in normative prose. An unresolved initial-scope requirement must not be silently deferred while still being advertised as satisfied. Pin the complete revised candidate before execution and identify it precisely when reporting conformance; partner adoption remains a separate status.
4. Execute independently defined controls. Freeze the derived source before execution. Independently read authored fixtures in headless OpenUSD, native OpenUSD and a live OV stage where relevant. Compare each with an authority-derived expected result, not merely with each other. Record source preservation and expected failures.
5. Audit after implementation. Trace every authored geospatial field and observable interpretation back to the proposal. Check the reverse trace for required results absent from tests. Internal implementation choices must not invent scene facts or normalize unspecified syntax.
6. Deliver the actual run. Derive the README from the receipt, then derive the review body and editable slides from the README. Lead with proposal quality, exact stopped portions and the evidence actually executed. Replace current delivery artifacts together and retain historical evidence in Git history. Publish to the existing fork draft when authorized.

It delivers a specification-stopped receipt with exit code 2 while G03/G04/G06/G07 remain open. Full model placement, Hydra geometry and resolved-scene exports remain stopped. Test or consumer failures are execution failures, not a successful stopped receipt.
